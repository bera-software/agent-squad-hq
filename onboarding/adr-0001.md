# 1. Record architecture decisions

Date: TODO(owner): the date this project was onboarded

## Status

Accepted

## Context

We need to record the architectural decisions made on this project.

This codebase is developed largely by AI agents under human direction.
Agents have no memory between runs; the repository is their only shared
memory. Decisions that are not written down will be silently violated.

## Decision

We will use Architecture Decision Records, as described by Michael Nygard in
"Documenting Architecture Decisions"
(https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions):
one short Markdown file per decision in `docs/adr/`, numbered sequentially,
written from `0000-template.md` (Title, Status, Context, Decision,
Consequences, plus the Impact section this squad's reviewer checks for).

ADRs are binding on all agents and humans until superseded by a later ADR.
The PR reviewer checks conformance to any ADR a PR links or touches. Before
taking a number, check the existing ADRs and every open PR's `docs/adr/`
files, so concurrent design PRs do not collide.

The project's architectural baseline (structure, layering, key technology
choices) is recorded in its own ADR, the next one after this. Layering rules
that can be checked mechanically also live in the architecture config the
hub's `arch` gate runs (for example `.dependency-cruiser.cjs` or
`.importlinter`), and the ADR links it.

## Impact

**Business impact:** a little more process per decision, in exchange for
consistent behaviour from agents over months.
**Technical impact:** the quarterly architecture review and new contributors
get a real decision history to reason over.

## Consequences

Significant changes start with a design PR. Superseded ADRs stay in place,
marked as superseded and linking their successor, so the history remains
readable.
